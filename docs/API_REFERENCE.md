# VulnWatch API Reference

## 1. Overview

VulnWatch exposes a FastAPI-based REST API for the VAPT, SOC, target-scanning, investigation, dashboard, and reporting workflows.

Backend:

```text id="x4p7k2"
FastAPI
   ↓
PostgreSQL
```

Default local backend:

```text id="j8m3q5"
http://127.0.0.1:8000
```

Interactive API documentation is available through Swagger UI:

```text id="v6n2r9"
http://127.0.0.1:8000/docs
```

The API is intended for the authorized VulnWatch laboratory environment.

---

# 2. API Authentication

Protected API endpoints use an API key.

The key is configured through:

```text id="c5w8m1"
VULNWATCH_API_KEY
```

The client sends the key using:

```text id="p7q3k9"
X-API-Key: <your-api-key>
```

Conceptually:

```text id="h2d6v8"
Client
  ↓
HTTP Request
  ↓
X-API-Key
  ↓
FastAPI Authentication
  ↓
Endpoint
```

If the API key is missing or incorrect, the protected endpoint returns:

```text id="s9f4n2"
401 Unauthorized
```


# 8. Scan Import API

The scan-import API receives Nmap XML results.

Conceptually:

```text id="m7p2c5"
POST /api/v1/scans/import
```

Purpose:

* Receive Nmap XML
* Parse scan information
* Create or update scan data
* Create/update assets
* Create/update services
* Associate discovered information with the database

Workflow:

```text id="f8n3q6"
Nmap
 ↓
XML
 ↓
POST /api/v1/scans/import
 ↓
XML Parser
 ↓
Asset / Service Processing
 ↓
PostgreSQL
```

The import operation is protected by API authentication.

---

The Scans API provides access to stored scan information.

A scan represents a VAPT discovery operation and its imported results.

The scan information can be used by the frontend to display:

# 14. Correlations API

The Correlations API provides relationships between SOC alerts and known vulnerability information.

The correlation engine connects:

```text id="b7v3n9"
Alert
  +
Service Vulnerability
  ↓
Correlation
```

The documented matching logic uses the alert destination IP and vulnerability target/asset relationship.

The correlation priority uses the higher severity between the alert and vulnerability.

# 16. Target Scan API

The Target Scan API provides browser-triggered scanning functionality.

The primary workflow starts with:

```text id="p6r3w8"
POST /api/v1/target-scan/start
```

The request initiates a scan job for an authorized target.

The workflow is:

```text id="c9m4q2"
Browser
  ↓
Target Scan API
  ↓
Target Validation
  ↓
Scan Job
  ↓
Kali Agent
  ↓
Nmap
```

---

# 17. Target Scan Security

The target-scan workflow validates the requested target before allowing scanner execution.

Important controls include:

* API authentication
* IP validation
* Authorized network enforcement
* Duplicate scan prevention
* Job-state management
* Nmap timeout
* `shell=False`

Conceptually:

```text id="n8p2v6"
Requested IP
    ↓
Authentication
    ↓
IP Validation
    ↓
Authorized Network
    ↓
Duplicate Check
    ↓
Create Scan Job
```

# 18. Target Scan Job API

The target scan is implemented as a job-based workflow.

The documented job states are:

```text id="f5k9s3"
PENDING
RUNNING
COMPLETED
FAILED
```

The Kali scanner agent obtains pending work from the backend.

Conceptually:

```text id="q7m3d8"
Target Scan Request
       ↓
PENDING
       ↓
Kali Agent
       ↓
RUNNING
       ↓
Nmap
       ↓
XML Result
       ↓
Import
       ↓
COMPLETED
```

---

# 19. Target Scan Job Claiming

The job-claiming workflow uses a database locking strategy based on:

```text id="r4v8k1"
FOR UPDATE SKIP LOCKED
```

This allows a scanner worker to safely claim an available job.

The purpose is to reduce the possibility of two workers processing the same pending scan job.

---

# 22. Reports API

The Reports API generates an asset-level security report.

The documented report endpoint is:

```text id="m9k4c7"
GET /api/v1/reports/{asset_id}
```

The endpoint requires API authentication.

The report combines information from:

* Asset
* Services
* Vulnerabilities
* Findings
* Security events
* Alerts
* Correlations

---

# 23. Report Structure

The documented report contains the following major sections:

```text id="v2q8s4"
1. Header
2. Executive Summary
3. Scope & Methodology
4. Risk Summary
5. Target & Asset Information
6. Open Ports & Services
7. Vulnerabilities
8. Detailed Findings
9. Security Monitoring
```

The report generator also deduplicates CVEs so that the same CVE is not unnecessarily repeated as separate vulnerability entries.

# 35. Current API Limitations

The current project has several documented API limitations.

## Rate Limiting

A dedicated API rate-limiting layer is not currently implemented.

## Automated API Tests

The project does not currently contain a formal automated pytest API test suite.

## Production Authentication

The current API-key model is suitable for the documented authorized lab but should not automatically be considered a complete production identity and access-management system.

## API Documentation Synchronization

Swagger reflects the actual FastAPI implementation, so this document should be updated whenever endpoint contracts change.

# 37. API Interview Explanation

A concise interview explanation is:

> "VulnWatch uses FastAPI to expose REST APIs for both VAPT and SOC workflows. The API handles Nmap scan imports, assets, services, vulnerabilities and findings on the VAPT side, while security events, alerts, correlations and investigations form the SOC side. Protected endpoints use an X-API-Key mechanism, request data is validated with Pydantic, database queries are parameterized, and target scanning additionally validates the requested IP against the authorized network before creating a scan job."

---

# 38. Safety Scope

The VulnWatch API is intended for the authorized project laboratory.

Target-scanning functionality must only be used against systems that are:

* Owned by the user
* Explicitly authorized
* Part of an isolated cybersecurity lab
* Intended for security testing

The API must not be used to bypass authorization or scan unrelated systems.
